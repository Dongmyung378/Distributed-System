# 포트폴리오: 분산 채팅과 예약 시스템 (Distributed Chat and Reservation Systems)

[English](PORTFOLIO.md) | [한국어](PORTFOLIO.ko.md) | [프로젝트 안내](../README.ko.md)

## 1. 개요

**최초 개발:** 2024년 9월부터 12월. **안정성 보강:** 2026년 10월.

Python으로 두 종류의 네트워크 애플리케이션을 구현했습니다. Talk는 줄바꿈 기반 TCP 프로토콜로 동시 접속자의 메시지를 처리합니다. Hotel Wedding Planner는 HTTP 클라이언트와 로컬 호텔 및 밴드 API, SQLite로 같은 슬롯의 예약 쌍을 찾습니다. 후속 개선에서는 초기 기능을 유지하면서 자원 사용을 제한하고 장애 후 결과를 복구할 수 있는 경로를 보강했습니다.

포트폴리오에서 보여 주는 역량은 프로토콜 처리, 동시성 제어, 트랜잭션과 장애 복구입니다. AI 기능을 포함한 서비스를 운영할 때에도 필요한 기반 역량을 네트워크와 예약 일관성 문제를 통해 설명합니다.

## 2. 결과

종료 처리와 처리 결과 재확인을 수정한 뒤 **Windows Python 3.10.21과 3.12.7에서 89개 검사를 모두 통과**했습니다. 총 178회 실행에서 실패와 오류, 생략은 0건이며 두 실행의 현재 소스 해시가 일치합니다. 초기 5개 검사도 유지했습니다. [CI 오류 수정 검증](reports/ci-repair-verification.json)에 로컬 실행 원자료를 연결했습니다. 자동화된 교차 플랫폼 실행 결과는 [GitHub Actions](https://github.com/Dongmyung378/Distributed-System/actions/workflows/ci.yml)에서 확인할 수 있습니다.

보존한 이전 소스 기록은 **4개 환경에서 환경별 85개 검사**, 총 340회를 실패와 오류, 생략 없이 통과했습니다. 해당 검증 보고서와 아래 벤치마크는 당시 자료이며 수정한 소스를 다시 측정한 결과는 아닙니다.

느린 연결 1개와 정상 수신자 3개를 둔 같은 실험을 각 버전에서 3회 수행했습니다. 계획한 수신은 매회 900건이며 **초기 3건에서 개선 후 900건**으로 늘었습니다. 초기에는 300회 방송 중 48회만 시도하고 47회를 소켓에 전송했으므로 미완료 관찰을 메시지 유실률로 해석할 수 없습니다. 정상 60개 연결의 회차별 p95 중앙값은 **1.6338ms에서 3.2020ms**로 증가했습니다. 자원 사용 수치는 서버와 측정 클라이언트를 함께 포함합니다.

기존 4개 환경 기록은 **Windows Python 3.10.22 / 3.12.7, WSL Ubuntu Python 3.10.22 / 3.12.3**을 사용했습니다. 각각 분리한 가상환경에서 잠금 파일로 의존성을 설치했습니다. Linux는 별도 소스 복사본을 사용했으며 당시 4개 실행 사이의 소스 해시가 일치합니다. WSL은 같은 물리 컴퓨터를 사용합니다. 로컬 수정 검증은 두 Windows 환경을 다루며 성능 벤치마크는 원래 소스 기준의 측정값을 유지합니다.

| 근거 | 확인할 수 있는 내용 |
| --- | --- |
| 실제 소켓 채팅 검증 | 초기 명령, UTF-8 분할 수신, 여러 명령의 동시 수신, 등록 순서 경쟁, 자원 제한, 느린 수신자, 재접속과 종료 |
| HTTP와 DB 검증 | 예약 소유자 구분, 충돌 처리, 멱등성 요청, 처리 기록 보존, 조건부 취소 |
| 복구와 CLI 검증 | 응답 유실 후 재확인, 새 예약 보호, 파일 저널을 사용한 재시작 복구 |
| 공통 벤치마크 | 명시한 루프백 조건에서 정상 사용자가 실제로 받은 건수와 누락 및 중복, 지연 분포 |

운영 환경의 최대 용량이나 인터넷 성능, 채팅의 영속 전달, 두 서비스의 원자적 예약을 입증한 결과는 아닙니다.

## 3. 해결하려던 문제

명령이 정상 실행되는 것만으로 장애를 잘 처리한다고 판단하기는 어려웠습니다. 끝나지 않는 입력이나 등록하지 않은 연결은 자원을 점유할 수 있고, 메시지를 읽지 않는 사용자는 동기식 전체 전송을 지연시킬 수 있었습니다. 등록 확인과 다른 사용자의 메시지 사이에도 명확한 순서가 필요했습니다.

예약에서는 서버가 이미 성공한 뒤 클라이언트만 응답을 받지 못할 수 있습니다. 이때 요청을 무조건 다시 보내거나 이전 작업을 무조건 취소하면 결과를 잘못 판단하거나 같은 슬롯에 새로 생성된 예약을 삭제할 수 있습니다. 과거의 성공 기록을 복구할 때도 해당 예약이 현재까지 유지되는지 확인해야 합니다.

## 4. 설계와 선택

Talk는 연결별 수신 스레드를 유지하고 크기가 제한된 FIFO 큐와 송신 스레드를 추가했습니다. 접속 수와 입력 크기, 등록 대기시간과 송신 시간을 명시적으로 제한합니다. 느린 수신자를 격리하는 대신 스레드 수가 늘어나는 비용을 수용한 설계입니다. 등록 확인을 큐에 넣기 전에는 새 사용자명을 공개하지 않습니다.

정상적인 거절과 종료는 마지막 응답을 보낸 뒤 소켓의 송신 방향을 닫고 기존 종료 예산 안에서 읽지 않은 입력을 버립니다. 계속 입력을 보내도 연결을 무기한 점유할 수 없으며, 실패한 연결을 정리한 뒤 `send_failures`를 갱신합니다.

Hotel은 예약 변경과 처리 결과를 같은 SQLite 트랜잭션으로 저장합니다. 재시도는 같은 작업 키를 사용하고, 보상 취소는 그 작업이 생성한 예약 세대가 맞는지 검사합니다. CLI는 요청보다 먼저 의도를 기록하고 확인할 수 없는 결과를 이후 복구 대상으로 남깁니다.

처리 결과 재확인은 읽기 전용 GET의 허용 시도 횟수를 `max(2, client.retries)`로 정하고 한 번의 조회에 정해진 기존 `max_elapsed` 예산을 공유합니다. 변경 POST를 추가하지 않고 변경 요청의 재시도 상한을 유지하며, 성공으로 알리기 전 현재 호텔과 밴드 예약 쌍을 입증하는 조건도 유지합니다.

대화형 예약 CLI는 영속 저널과 같은 저널을 공유하는 프로세스 사이의 잠금을 사용합니다. 함수를 직접 호출할 때는 파일 저널을 명시적으로 전달하지 않으면 메모리 저널을 사용합니다. 자동 매칭은 별개의 수동 예약을 보존하고 불필요한 예약 정리는 사용자가 메뉴 7을 선택했을 때 수행합니다.

상태 전이와 잠금 범위, API 호환성은 [설계 문서](ARCHITECTURE.ko.md)에 정리했습니다.

## 5. 실험과 재현

```bash
python -m pip install -r requirements-dev-lock.txt
python -B scripts/verify.py --output target/verification.json
python -B scripts/benchmark.py --project . --scenario all --trials 3 --label current-source --output target/benchmark.json
```

검증은 임시 포트와 SQLite DB를 사용합니다. 외부 서비스를 준비하거나 데모 서버를 미리 실행하는 대신 통제된 오류와 실제 subprocess로 실행 흐름을 확인합니다.

정상 채팅 조건은 수신 사용자 2명, 10명, 30명, 60명으로 나누고 회차별 예열 5회와 측정 20회를 사용합니다. 느린 수신자 실험은 읽기를 멈춘 연결 하나를 추가하고 그 연결의 소켓 버퍼를 제한합니다. 초기 버전과 개선 버전은 같은 스크립트와 메시지, 같은 버퍼 조건으로 측정합니다. 새로 추가한 큐와 송신 제한시간 설정은 개선 버전에만 존재합니다.

초기 소스는 `1504ab3` 커밋으로 보존했습니다. 별도 디렉터리로 내보낸 뒤 `--project`에 경로를 전달하면 현재 소스를 덮어쓰지 않고 같은 도구로 비교할 수 있습니다. p50이나 p95 지연을 읽기 전에 실제 수신과 누락 수를 함께 확인해야 합니다. 일부 메시지만 도착한 상태의 지연을 전체 성공으로 해석하지 않습니다. 반복 회차는 순서대로 실행하며 독립된 운영 호스트 여러 대를 측정한 결과는 아닙니다.

## 6. 실패 분석과 한계

- 송신 큐에 넣었거나 소켓에 모두 썼다는 사실만으로 사용자가 읽었다고 볼 수 없습니다. 영속 대화 이력과 재전송 계약은 없습니다.
- 느린 수신자 격리를 위해 연결마다 송신 스레드를 추가했습니다. 연결 수와 큐 상한으로 자원 비용을 제한합니다.
- 서버 처리 기록은 자동 만료시키지 않습니다. 장기 보존과 디스크 관리는 별도의 운영 정책이 필요합니다.
- 재시작 복구에는 파일 저널이 필요합니다. 기본 직접 함수 호출의 메모리 저널은 종료 후 남지 않습니다.
- 서비스나 처리 결과를 확인할 수 없으면 복구가 미해결로 남습니다. 이를 성공이나 실패로 임의 확정하지 않습니다.
- 호텔과 밴드의 현재 예약 세대는 따로 조회합니다. 확인 도중이나 완료 이후 외부 사용자가 예약을 바꿀 수 있습니다.
- `max_elapsed`는 재시도 예산이며 개별 요청과 전체 워크플로의 절대 실행시간을 보장하지 않습니다.
- 데모 인증과 로컬 HTTP 서버는 재현 가능한 로컬 실행을 대상으로 합니다. 공개 서비스에는 별도의 보안과 운영 설계가 필요합니다.

## 7. 실행 예시

Talk는 서버 하나와 클라이언트 두 개를 열고 Alice와 Bob으로 등록합니다. 전체 메시지와 개인 메시지, 사용자 목록과 종료 확인을 순서대로 볼 수 있습니다. 갑작스러운 연결 종료와 느린 수신자 처리는 자동 검증에서 별도로 확인합니다.

Hotel은 `Hotel/local_api.py`와 `Hotel/booking.py`를 실행합니다. 새 데모 DB에서 메뉴 6은 가장 이른 공통 슬롯을 예약합니다. 메뉴 1부터 5까지의 조회와 수동 조작은 유지했고 메뉴 7에서 필요한 정리를 수행합니다. 자동 예약이 중단되었다면 같은 파일 저널로 CLI를 재시작해 복구합니다. 복구 시험을 위해 API DB를 초기화하면 미해결 작업을 판단할 처리 기록도 사라지므로, 같은 데이터와 저널을 유지해야 합니다.
